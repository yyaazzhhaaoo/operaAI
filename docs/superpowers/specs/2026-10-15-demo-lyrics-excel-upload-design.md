# 上传示范时附带逐字数据（Excel）设计

**关联**：`DOC_ISSUES.md` 第 20 条（本设计推翻它的一半结论）；数据源 `穆桂英挂帅_逐字声学数据_4.3.xlsx`；模板依据《8-数据准备清单-V1.0》4.3 节「戏词逐字声学数据模板（每段一张表）」。

## 1. 背景与目标

示范库的上传链路现在**只产段、不产字**：`library_repo.replace_segments` 硬写 `lyrics_json=None`（第 20 条的理由是「没有 ASR 组件，音频给不出汉字」）。于是 Demucs 切出来的每段都是空壳——跟唱页没有基准音高，标注页没有可标注的字。

汉字教师手上本来就有，只是不在音频里，而在一张按模板做的 Excel 里。**目标：上传示范时可选地附带这张 Excel，把逐字数据写进 `segments.lyrics_json`。**

范围只到入库。读取通路（C3 `GET /api/segments/<id>` → `library_service._normalize_lyrics`）早就完成，本设计不改它，也不改示范库详情页的展示。

## 2. 现状（实测）

### 2.1 Excel 的实际结构

11 个页 = 1 个「说明」页 + 10 个数据页。数据页命名 `第N段_唱词标题`，表头六列：

`字序 | 字 | 音高 | 起始时间(s) | 结束时间(s) | 演唱技巧提示`

- 音高形如 `56 (G#3)`（MIDI 号 + 音名）。
- 时间列**不一定是数字**：可能是文字 `不在修剪版中`。
- **没有时值列** —— `note` 由字时长反推，见 §3.5。

逐页实测：

| 页 | 字 | 无时间 | 该页最小 start | 段内时长 |
|---|---|---|---|---|
| 第1段_辕门外三声炮如同雷震 | 10 | 10 | — | — |
| 第2段_天波府里走出来我保国臣 | 11 | 11 | — | — |
| 第3段_头戴金冠压双鬓 | 7 | 3 | 0.00 | 3.98 |
| 第4段_当年的铁甲我又披上了身 | 11 | 0 | 3.98 | 21.04 |
| 第5段_帅字旗飘入云 | 6 | 0 | 25.02 | 4.97 |
| 第6段_斗大的穆字震乾坤 | 8 | 0 | 29.99 | 5.81 |
| 第7段_上啊上写着 | 5 | 0 | 35.80 | 9.40 |
| 第8段_浑啊浑天侯 | 5 | 0 | 45.20 | 3.97 |
| 第9段_穆氏桂英 | 4 | 0 | 49.17 | 3.09 |
| 第10段_谁料想我五十三岁又管三军 | 12 | 0 | 52.26 | 20.28 |

合计 79 字，其中 **24 字无时间**（第 1 段 10 字、第 2 段 11 字、第 3 段前 3 字「头戴金」）。这 24 字对应的演唱在修剪版里不存在：说明页记载音频来源是 `穆桂英挂帅修剪版.wav`（72.54 s = 原曲去掉开头 39.46 s），它们正好唱在被剪掉的那 39.46 s 里。

### 2.2 库里已经躺着一份同源数据（`teacher_demos.id=16`）

`SELECT` 实测：该示范 10 段，**每段 `lyrics_json` 都非空**。它与本 Excel 的关系是：

- **字、技巧提示完全一致**（连 `归韵到'eng'`、`颤音润腔，喉部放松` 都逐字相同）。
- **时间已被改成段内相对**：每段都从 `0.0` 重新起算。第 4–9 段的 `duration`（21.04 / 4.97 / 5.81 / 9.40 / 3.97 / 3.09）与「按本设计 §3.3 算出的」逐秒吻合，第 10 段差 0.07 s。这反证了「转段内相对」就是当初的做法。
- **第 1、2 段的 `duration`（19.48 / 11.12）与第 3 段（10.56）是另外编的**——Excel 里这三页没有可用时间，算不出这些数。
- **`note`（`NOTE_2` / `NOTE_DOT_4` …）在 Excel 里没有对应列**。它和字长也对不齐（`震` 实际 0.82 s 却标 `NOTE_DOT_4`，按下面反推出的拍长该是 `NOTE_2`；`同` 0.14 s 标 `NOTE_16`，比 1/16 拍长两成），说明那份是**人照乐谱标的**，不是量化出来的 —— 这正是本设计 §3.5 的反推值不会与它逐字相同的原因。
- **当前库里的 `midi` 与 Excel 对不上**（Excel 首字 56，库里是 70），但 2026-10-14 的 `segments-backup-20261014.sql` 里是 56、与 Excel 一致。

**结论：这份是手工灌进去的测试数据，只可参考格式、不可参考数值。** 它也不可能出自现有代码——`replace_segments` 硬写 `lyrics_json=None`。本设计不迁移、不修改它。

### 2.3 前端要求 `start` 是**段内相对**秒数

这一条决定 §3.3，不是可选项。`sing_along.html` 实测三处：

| 位置 | 代码 | 含义 |
|---|---|---|
| `:1172` | `if (t >= ly.start && t < ly.start + ly.duration)` | `t` 是**本段播放到第几秒** |
| `:1289` | `elapsed > (seg.duration + 0.5)` | `elapsed` 同上，与段长比 |
| `:923` `:1017` | `timeToX(ly.start)` | 直接画在时间轴上 |

若把 Excel 的全局时间原样入库，第 5 段的字会带 `start: 25.02`，而播放该段时 `elapsed` 从 0 起——**永远匹配不上**，那一段跟唱时不会高亮任何字。

同一批代码对缺失值是有容错的（`:923` `if (!Number.isFinite(ly.start)) return;`、`:1170` 同样跳过），所以 `start` 为 `null` 的字会被安静跳过。

### 2.4 `annotation.html` 对 `start` 为 `null` 会抛异常

`annotation.html:651` 的分支条件是 `item.pitch !== null`，而**没时间的字音高是有值的**（Excel 给了），于是会走到 `:655` 的 `item.start.toFixed(1)` —— `null.toFixed` 抛 `TypeError`，`renderLyrics` 当场中断，歌词网格渲染到一半就停。`:684` 的 `item.start.toFixed(2)` 同理。**这是 §3.3 引入 `null` 时间后必须一起补的容错**，不是可选项。

（该页对 `note` 为空已有容错：`:620` `if (note === null || note === undefined) return "—";`。）

## 3. 设计

### 3.1 上传接口的分支

`POST /api/demo/library/upload` 增加一个**可选**的 multipart 字段 `excel`：

| 传了 `excel` | 没传 `excel` |
|---|---|
| 解析成 segments 写入，**不投 Demucs 任务** | 现状不变：投 `demucs` 队列，由 worker 切分（`lyrics_json` 仍为 `None`） |
| 响应 `{"demo_id": N, "task_id": null}` | 响应 `{"demo_id": N, "task_id": "<hex>"}` |
| 秒级返回，前端不弹「处理中」 | 前端照旧轮询 |

两条路都回填 `audio_files.duration_sec`。

**状态不写 redis**：详情/状态接口走 `parse_service.status()` 已有的派生路径（`segments` 有行 → `parsed`），有 Excel 时它天然给出正确结果，前端即便轮询也是第一次就拿到 `parsed`。

### 3.2 页 → `segments` 行

一页 = 一行：

| 来源 | 落库 |
|---|---|
| 页名 `第N段_唱词标题` 的 N | `seq` |
| 页名里 N 之后的唱词 | `title` |
| 该页的有效字 | `lyrics_json` |
| §3.3 算出的段内时长 | `duration` |

### 3.3 逐字字段映射

每字落成 `{word, midi, start, end, note, tip}`——正是 `segments.lyrics_json` 列注释里已有的形状：

| Excel 列 | 字段 | 规则 |
|---|---|---|
| 字 | `word` | 去空白后为空、或非字符串 → **跳过该行**（与 `_normalize_lyrics` 的丢弃口径一致） |
| 音高 `56 (G#3)` | `midi` | 取开头的整数部分；**括号里的音名丢弃**（前端 `midiToNote(pitch)` 能算出来，不重复存） |
| 起始时间(s) | `start` | 见下「转段内相对」；不是数字（如 `不在修剪版中`）→ `null` |
| 结束时间(s) | `end` | 同上 |
| 演唱技巧提示 | `tip` | 原文；空 → `null` |
| —（本表无此列） | `note` | 由字时长反推，见 §3.5 |

**时间转段内相对**：取该页**有时间的字**里最小的 `start` 作基准 `base`，每个有时间的字落 `start - base`、`end - base`。该页一个有时间都没有（第 1、2 段）→ 全页字的 `start`/`end` 均为 `null`。

第 3 段是混合情形：`base = 0.00`（来自「冠」），「冠」及之后 4 字保持原值，「头戴金」三字为 `null`。

**段时长** `duration` = 该页**最后一个有时间的字的 `end` 减去 `base`**（也就是转相对之后末字的 `end`）：该页有时间时取值见 §2.1 表末列；整页无时间（第 1、2 段）→ `null`。中间缺时间的字（如第 3 段的「头戴金」）不影响这个计算，它们只是没有自己的 `start`/`end`。

### 3.4 失败与回滚

解析失败一律 **400 且整批回滚**——音频也不会留下（与音频同一次事务，`demo_library_add` 末尾那次 `commit` 是唯一提交点）。

| 情况 | 响应 |
|---|---|
| 文件打不开 / 不是 xlsx | 400「逐字数据文件无法解析，请确认是 .xlsx」 |
| 没有任何 `第N段…` 命名的页 | 400「逐字数据里没有找到『第N段_…』格式的数据页」 |
| 某页缺必需列 | 400「第3段 缺少列：起始时间」 |
| 某页字表为空 | **不报错**，该段 `lyrics_json` 存 `[]`——「这一句还没标」是合法状态 |

必需列：字、音高、起始时间、结束时间。演唱技巧提示可缺（缺则该字段为 `null`）。列**按表头名定位**（第 1 行），不认死列号；列名比较时容忍 `起始时间(s)` 这类单位后缀。

### 3.5 `note`（时值）：由字时长反推，拍长按曲自适应

Excel 里没有时值列，但**有时长**——而时值本来就是「这个字唱多长」的另一种表达。所以 `note` 从时长推算：

```
note = 最近档位(字时长 / B)        B = 这一首曲子的一拍秒数
```

**B 不写死，按曲自适应估出。** 时值词表（`NOTE_1` … `NOTE_32` 及附点）只表达「几分之一拍」、不含绝对时间，而每首曲子的速度不同——写死一个常量，换一首快板曲子会让所有字的时值系统性偏档。

估法是**网格搜索**：在 0.3–3.0 s 内按 0.01 s 遍历候选 B，对每个候选把全体字量化一遍、累加误差，取误差最小的那个。三条约定：

- **距离用对数尺度**（`|log2(比例) − log2(档位)|`），因为档位是等比数列——用线性距离会让长档位附近的边界偏得离谱。
- **样本是该曲全部段落的字**，不是单段：一段只有几个字，估出来的拍长会抖；拍速是一首曲子的属性。**无时间的字不参与估计**（第 1、2 段整段、第 3 段的「头戴金」）。
- **退化保护**：有时间的字不足 5 个时（比如整张表只有一段标了时间），网格搜索会退化成「把那一个字完美量化」，此时直接用默认拍长 `DEFAULT_BEAT_SEC = 1.9`（从 §2.2 那份反推而来、**未经真实素材标定**，同 `TOP_DB` 的性质）。

**候选档位 = 前端词表的 11 个标签**：`1, 1/2, 1/4, 1/8, 1/16, 1/32` 拍，以及它们的 1.5 倍（附点）。注意**词表里没有 `NOTE_DOT_1`**——1.5 拍这个标签不存在，所以：

- 比例 > 1.5（超出词表能表达的最长档）→ `note` 留 `null`。库里那份也是这么处理的（`声` 4.81 s、`炮` 6.11 s 都是空），长拖腔不属于常规时值。
- 其余按对数距离取最近档。

**估出的 B 只记日志，不入库、不加列**：字时长本来就在库里，任何时候都能重算。

**这是启发式估计，不等于乐谱时值。** §2.2 已证库里那份是人照谱标的，两者不会逐字相同——人唱的总比谱面松一点。它的定位是给标注页一个**随曲子速度走**的参考值；若将来拿到真正的乐谱时值数据，应由那份数据覆盖它。

### 3.6 新模块 `app/services/lyrics_excel.py`

纯函数，不碰 DB、不碰 flask、不引用 `request`：

```python
def parse_segments(blob: bytes) -> list[dict]:
    """xlsx 字节流 → [{seq, title, duration, lyrics}]，失败抛 BusinessError(400, ...)"""
```

这样它可以脱离整个应用被单独喂文件测试（项目无测试框架，验证靠临时脚本，见 §7）。

依赖：**新增直接依赖 `openpyxl`**（纯 Python，Mac/Linux 都装得上，不影响 §「requirements-demucs.txt 的 linux 平台标记」那套逻辑）。写进 `requirements.txt`，与其他直接依赖同规矩钉死版本。

### 3.7 `library_repo.replace_segments` 支持 `lyrics`

现在它对每行硬写 `lyrics_json=None`。改为读 `s.get("lyrics")`，缺省 `None`——**Demucs 那条路一行不用改**，行为不变。

### 3.8 `probe_duration` 提到 `audio_service`

`parse_service._master_duration` 提升为 `audio_service.probe_duration(path)`，两条链路共用；`parse_service` 改为调用它。理由：上传接口（同步）与解析任务（worker）都要回填 `audio_files.duration_sec`，两处各写一份迟早会漂移。

### 3.9 前端上传表单（`demo_library.html`）

- 弹窗内新增一行「逐字数据（可选）」文件框，`accept=".xlsx"`，**不参与** `uploadTitle` 的自动回填（现有 `onFileSelect` 会在标题为空时用文件名填标题，那是音频文件的逻辑，不能被 Excel 抢走）。
- `doUpload` 把文件 append 进同一个 `FormData`，字段名 `excel`。
- 响应 `data.task_id` 为空时：不调 `showProcessingModal`、不 `startPolling`，改为 toast「上传成功，已按逐字数据建段」并刷新列表与详情。

### 3.10 `annotation.html` 补 `start` 空值容错

`renderLyrics` 里两处：

- `:655` `item.start.toFixed(1)` → 无有效值时显示 `—`
- `:684` `item.start.toFixed(2)` → 同上

判定写 `Number.isFinite(item.start)`（与 `sing_along.html` 同口径），不写 `!== null`——`NaN` 也会让 `toFixed` 输出 `NaN`。

## 4. 关键决策与理由

| 决策 | 理由 |
|---|---|
| Excel 选填 | 老资源、临时试传不受影响；两条路共存，后端分支只有一处 |
| 有 Excel 就不投 Demucs | 段边界由唱词句决定，Demucs 的停顿切分不再需要；一次 8–15 分钟的开销省掉，且不再有「段数与句数对不上、字该往哪段放」的问题 |
| 同步解析、不落盘 | 毫秒级的事不该做成异步：不需要 worker、不需要轮询、不需要 redis 状态、不需要给 `teacher_demos` 加列存路径。失败即整批回滚，也没有「异步重试」的诉求 |
| 时间转段内相对 | §2.3：前端拿 `start` 与「本段已播放秒数」比，全局时间会使跟唱页匹配失效 |
| 丢弃音名 `G#3` | 前端有 `midiToNote(pitch)`，音名是算出来的 |
| `note` 由时长反推、拍长按曲自适应 | §3.5：词表只表达「几分之一拍」、不含绝对时间，而每首曲子速度不同——写死一个拍长会让换曲后所有字的时值系统性偏档 |
| 缺时间的字照存 | 唱词要完整；前端两页对缺值都已有（或本次补上）容错 |

## 5. 容错口径

- **不校验 Excel 时间轴与音频是否对得上**。已确认上传的是与 Excel 同源的修剪版；「开头被剪掉 39.46 s」这种合理偏差与「传错音频」在数据上无法区分，宁可不做假警报。
- 无时间的字（24 个）落 `start`/`end` = `null`：跟唱页跳过其高亮、标注页显示 `—`，**字本身照常显示**。
- 第 1、2 段的 `duration` 为 `null`：跟唱页 `seg.duration` 非有限时按 0 处理并显示「时长未知」（该页已有分支）。
- `note` 仍有 `null` 的可能：超 1.5 拍的长拖腔（§3.5）、以及整段无时间的字。标注页对空 `note` 已有 `—` 分支。

## 6. 非目标

- 不改 `schema.sql`（`segments.lyrics_json` 本来就能装，`start/end` 在 JSON 内，不新增列）。
- 不改示范库详情页的展示（C2/C3 已能吐逐字数据，本轮不接 UI）。
- 不做「给已有示范补传/更换逐字数据」的接口——传错了重传整个示范即可；真需要时那是一个独立接口，比留档更有用。
- 不迁移、不修改库里的 `demo 16`（手工测试数据，§2.2）。
- 不支持 `.xls`/`.csv`（`openpyxl` 只读 xlsx）。

## 7. 验证

项目无测试框架，沿用「临时脚本 + curl + psql」：

1. 临时脚本喂真实 xlsx 跑 `parse_segments`，断言：10 段；总字数 79；无时间的字 24 个；第 3 段 `duration` = 3.98；第 4 段首字 `start` = 0.0；第 5 段首字 `start` = 0.0 且 `duration` = 4.97。
   另打印自适应估出的拍长 `B` 与逐字档位：`B` 应落在 **1.5–2.3 s**（§2.2 从库里那份反推出的是 ≈1.9 s，两者来源独立，可互相印证）；第 1、2 段的字全部无 `note`（本就没有时长）；超 1.5 拍的长音应留空（如第 4 段的「的」6.18 s、第 7 段的「啊」3.44 s）。
2. curl 真上传一次（音频 + Excel），psql 查 `segments` 行数与 `lyrics_json` 首字；确认 `parse/status` 立刻回 `parsed`。
3. curl 不带 Excel 上传一次，确认仍投 Demucs、行为与改造前一致（worker 未起时应停在 `parsing`）。
4. 坏文件（随便一个 txt 改名成 .xlsx）上传，确认回 400 且库里不留痕（`teacher_demos`/`audio_files` 都没多行）。
5. 浏览器打开 `annotation.html` 选中带 `null` 时间的字，确认网格不中断、显示 `—`。
